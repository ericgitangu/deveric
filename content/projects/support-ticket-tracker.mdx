# Context and problem

Support teams need a dependable way to create, triage, update, and close tickets while keeping the browser and API aligned on the same contract. A compact implementation is useful only if it preserves input validation and remains practical to run and test.

## Engineering approach

- **Typed API boundary.** FastAPI exposes validated ticket operations and a schema used to generate a TypeScript client, reducing handwritten contract drift.
- **Query paths designed for triage.** Relational storage and indexed filters support common ticket sorting and search without loading the complete record set into the browser.
- **A focused web workflow.** The Next.js client provides ticket creation, editing, and review against the asynchronous service API.
- **Reproducible local operation.** The API, database, and web application can be started together in a containerized development environment.

## Outcomes and trade-offs

The project brings ticket operations and service data into one small, testable application, with a generated client contract between the UI and API. Its deliberately focused scope favors clear CRUD and query behavior over a broader support-suite feature set.

## Stack

- Python, FastAPI, and SQLAlchemy
- PostgreSQL and schema-driven API documentation
- Next.js and TypeScript
- Docker Compose and automated tests
