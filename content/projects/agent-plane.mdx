# Context and problem

Turning a high-level project epic into actionable work requires decomposition, estimation, ownership, and review. A single opaque model response is difficult to trust or recover from when a generation is incomplete or proposes invalid work.

## Engineering approach

- **Structured agent workflow.** A decomposer, estimator, and assignee recommender produce typed proposals rather than free-form text; generated ownership is checked against the actual project roster.
- **Progressive streaming.** Server-sent events report completed stages so the board can update while the workflow runs instead of blocking on a single final response.
- **Recoverable execution.** Checkpoints support resuming after worker failures, while persisted run records provide an audit trail for reviewing prior proposals.
- **Bounded external work.** Per-workspace rate limits bound model usage; if the optional Redis dependency is unavailable, the limiter fails open so orchestration can continue while the cost guard is temporarily weakened.
- **Human decision at the boundary.** Proposed issues remain pending until a user accepts or rejects them, and accepted work retains a reference to its originating run.

## Outcomes and trade-offs

The project demonstrates a complete proposal-to-approval loop rather than treating generated text as completed work. Structured output, member validation, resumable execution, and explicit human approval address the main reliability challenges. Authentication and multi-region database behavior remain outside the prototype's demonstrated scope.

## Stack

- Python, FastAPI, SQLAlchemy, and Pydantic
- LangGraph orchestration and asynchronous task processing
- Next.js, TypeScript, and TanStack Query
- Distributed SQL, document storage, Redis, and Docker Compose
- Server-sent events, structured logging, and OpenTelemetry
