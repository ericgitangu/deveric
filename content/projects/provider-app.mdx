# Context and problem

Providers need a direct way to maintain their account and complete work-related tasks without routing every update through an internal operations team. The portal makes those workflows accessible from a mobile device while preserving the platform's existing identity and service rules.

## Engineering approach

- **Self-service account workflows.** Providers can review earnings and trip history, maintain required documents, configure payouts, and manage account-related tasks.
- **A dedicated application surface.** The portal keeps provider workflows separate from customer and staff screens while integrating with the shared API.
- **Static hosting with client-side data.** A Next.js static export is served under a stable path; the authenticated browser client communicates with the backend-for-frontend for mutations and account state.
- **Mobile-first interaction.** Responsive layouts and address/map components support common tasks on smaller screens.

## Outcomes and trade-offs

The portal reduces reliance on staff-mediated account updates and provides a consistent home for provider operations. Because the application is statically hosted, route prefixes and API configuration are explicit rather than inferred from a server-rendered runtime.

## Stack

- Next.js 16 App Router, React, and TypeScript
- Base UI, CSS Modules, Tailwind utilities, SWR, and Zod
- Shared REST/BFF integration and browser authentication
- Vitest and React Testing Library
