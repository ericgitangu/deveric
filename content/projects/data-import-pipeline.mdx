# Context and problem

Batch imports can introduce partial, duplicated, or low-quality data when validation and persistence are handled as one opaque operation. Operators need to understand what will be accepted, what will be rejected, and whether a failed attempt can be safely repeated.

## Engineering approach

- **Validate before persistence.** Each incoming row is checked against the expected schema, with rejected records included in the import report.
- **Make retries predictable.** Idempotent processing prevents duplicate writes when a batch is submitted again after an interrupted run.
- **Protect data quality.** A configurable rejection threshold can abort the transaction instead of leaving a partially accepted batch in the database.
- **Preview before changing state.** Dry-run mode produces the same validation report without persisting changes, giving operators a review step before applying an import.

## Outcomes and trade-offs

The pipeline makes batch behavior auditable and repeatable, with explicit controls for data quality and transaction boundaries. The trade-off is that imports with substantial rejection rates require an operator decision rather than silently accepting a partial result.

## Stack

- Python and PostgreSQL
- Docker-based local development
- Automated validation and integration tests
